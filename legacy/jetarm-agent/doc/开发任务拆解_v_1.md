# 《开发任务拆解与 OpenSpec 开发规范 v1》

## 0. 文档定位

本文档不再只是“任务列表”。
从现在开始，它同时承担两种角色：

1. 作为 JetArm 正式主线的阶段拆解文档
2. 作为后续 OpenSpec change 的阶段推进与实现约束文档

本文档回答以下问题：

1. 最终智能体到底要做成什么
2. 当前阶段为什么不能直接跳到 adapter、运行时或云端功能
3. 每个阶段的目标、输入、输出、冻结门槛是什么
4. OpenSpec change 应该如何选题、落地、验证、冻结资产
5. 哪些工作允许进入正式主线，哪些必须继续停留在验证、adapter 内部或 deferred

如果本文档与上位治理文档冲突，处理顺序固定为：

1. 先更新上位文档
2. 再回填本文档
3. 最后实施具体 change

## 2. 最终目标与当前纠偏

### 2.1 最终目标

项目最重要的最终效果不是“机械臂能执行几个固定动作”，也不是“先做一个会说话的 demo”。
最终目标是构建一个正式的 JetArm 智能体系统，使其能够：

- 与人进行自然语言对话
- 理解用户真实意图，而不是只做关键词触发
- 在任务含糊时主动澄清约束与目标
- 将自然语言任务转成结构化任务对象和计划
- 自动规划并执行多步复杂任务
- 在执行中结合感知、世界状态与安全约束动态调整
- 在失败时解释原因、选择恢复策略或向用户追问

### 2.2 当前阶段的正确定位

当前主线仍然处于“正式智能体之前的执行底座冻结期”。
前面进行的控制链、抓取链、官方链路、会话验证，不是最终产品本身，而是在为以下最终能力打底：

- 自然语言理解后的安全落地执行
- 面向复杂任务的结构化技能与世界状态
- 云边协同规划而不是云端直控

因此，当前不能把“完成一次 pick-place”误当成项目目标完成，也不能把“做出自然语言 demo”误当成正式主线成立。

## 3. 长期开发原则

### 3.1 北极星原则

所有阶段工作都必须服务于最终北极星能力：

`自然语言交互 -> 意图理解 -> 结构化规划 -> 板端安全执行 -> 状态反馈与失败解释`

### 3.2 资产优先原则

任何服务、话题、launch、脚本、动作流程、配置、标定参数、数据结构、接口、运行时模块、云端对象、文档结论，都必须先进入统一资产分类体系，再进入实现。

### 3.3 分阶段 gate 原则

每个阶段必须先完成自己的冻结目标，再进入下一阶段。
禁止跨阶段“凭感觉先写代码”。

### 3.4 板端安全边界原则

云端永远不能直接控制底层 ROS 控制原语。
板端是唯一正式执行边界。

### 3.5 先验证再封装原则

未验证或未冻结的官方能力，不得直接提升为正式主线 API。
需要先做验证 change，再做 adapter 或 runtime change。

### 3.6 legacy 隔离原则

`src/jetarm_demo_agent`、`remote/jetarm_executor` 和演示期文档只能作为证据来源或操作参考，不能悄悄回流成正式主线依赖。

## 4. 当前统一资产分类

所有项目资产必须属于以下五种状态之一：

- `verified_frozen`
- `verified_not_frozen`
- `documented_not_verified`
- `legacy_reference`
- `deferred`

所有技术资产还必须声明封装级别：

- `mainline_wrapper`
- `adapter_internal_only`
- `legacy_reference_only`
- `deferred`
- `governing_source`

本文档不重复定义这些状态的完整规则，状态解释以治理文档和资产总表为准。

## 5. 总体阶段划分

从正式主线视角，开发阶段应按以下顺序推进。

### Phase 0：治理与官方基线冻结

目标：

- 冻结最终架构、治理规则和资产总表
- 搞清板端实际环境、官方能力边界和控制层级

阶段产出：

- 上位架构文档
- 资产治理文档
- 项目资产总表
- 官方控制层级与基线文档

阶段 gate：

- 项目级 source of truth 建立完成
- 官方控制层级和主线/legacy 边界清晰

### Phase 1：官方板端能力全量验证与一阶段冻结

目标：

- 按官方层级验证一阶段必须能力
- 形成完整验证矩阵和冻结结论

阶段产出：

- Phase 1 完整验证矩阵
- 完整验证日志
- 冻结/未冻结结论

阶段 gate：

- 一阶段所需官方资产全部入表
- 每项资产都有明确结论
- 仍未冻结项有清晰阻断理由

### Phase 2：正式 board adapter 与配置资产冻结

目标：

- 在已验证资产上实现正式 board adapter
- 将标定、偏移、工作区约束、请求/结果对象正式化

阶段产出：

- board adapter
- calibration/config 资产
- board-side request/result contract

阶段 gate：

- adapter 不再依赖 legacy/demo
- 上层不再直接接触裸 ROS 控制接口

### Phase 3：skills、world state、board runtime 落地

目标：

- 将 adapter 之上的执行逻辑抽象成 skill
- 建立 world state
- 建立 board runtime / behavior tree

阶段产出：

- skill contract
- world state schema
- board runtime / BT execution

阶段 gate：

- 板端执行已具备结构化任务消费能力
- 失败、恢复、状态反馈可被 runtime 消费

### Phase 4：云端对话、意图理解与规划契约冻结

目标：

- 明确云端如何与人交互、如何表达意图、如何输出计划
- 冻结板端可接受的云端对象边界

阶段产出：

- 对话状态对象
- `TaskIntent`
- `ClarificationRequest`
- `ExecutionPlan`
- `BehaviorTreePlan`
- cloud-board protocol

阶段 gate：

- 云端对象可被板端验证和拒绝
- 云端仍不能直控底层动作

### Phase 5：自然语言复杂任务 MVP

目标：

- 打通“自然语言输入 -> 任务理解 -> 计划生成 -> 板端执行 -> 状态解释”的最小正式闭环

阶段产出：

- 多轮自然语言交互 MVP
- 复杂任务执行 MVP
- 失败解释与追问机制

阶段 gate：

- 系统不只会执行固定指令
- 系统能处理至少一类多步复杂任务

### Phase 6：稳定性、恢复性与交付冻结

目标：

- 将系统从“能跑”打磨为“可复现、可交付、可维护”

阶段产出：

- 稳定性报告
- 性能指标
- 交付与 handoff 资产

阶段 gate：

- 关键任务复现稳定
- 已知失败模式有清晰应对
- 后续实现者可不依赖聊天记录继续推进

## 7.2 Phase 1：官方板端能力全量验证与一阶段冻结

### P1-A：一阶段必需资产全量入表

必须覆盖：

- 底层控制：`sdk_node_6dof.launch`、servo move/stop/load、group motion、buzzer、LED
- 运动学服务：current pose、joint range、joint target、pose target、`fk.launch`、`ik.launch`
- 相机基础：RGB、Depth、CameraInfo
- 感知与坐标链：`camera_topic_invoke`、`color_threshold`、`color_space`、`color_detection`、`pixel_coordinate_calculation`、`object_attitude_calculation`、`coordinate_system_transformation`
- 规划与抓取链：`path_planning`、`positioning_clamp`、`color_sorting`、`object_sortting`、`/grasp`
- 系统入口与配置：`app_bringup.launch`、`base.launch`、`lab_config_client.py`

验收：

- 资产总表中不存在“一阶段关键资产未登记”状态

### P1-B：底层控制与运动学验证

目标：

- 验证单舵机、多舵机、夹爪、stop、运动学查询与求解接口

结论要求：

- 逐项写清 `verified_frozen` / `verified_not_frozen` / `documented_not_verified`
- 明确封装级别是否 `adapter_internal_only`

### P1-C：相机、识别、坐标与规划链验证

目标：

- 验证一阶段所需的视觉、坐标、规划、任务流基础

结论要求：

- 区分“控制面已通”“实际流程已通”“repeatability 已证明”

### P1-D：完整抓取链监督验证

目标：

- 对官方 `pick_place` 底座进行 supervised 验证

关键规则：

- 一次成功不等于 frozen
- 缺少重复性、退出语义、现场观察时，只能停在 `verified_not_frozen`

### P1-E：Phase 1 完整验证矩阵冻结

输出：

- `docs/baseline/phase1_full_validation_matrix.md`
- `logs/YYYY-MM-DD-phase1-full-validation.md`
- 结构化验证结果

验收：

- 一阶段所有官方资产都有结论
- `pick_place` 是否冻结有明确 gate

## 7.6 Phase 5：自然语言复杂任务 MVP

### P5-A：多轮自然语言交互

系统必须支持：

- 任务接收
- 目标澄清
- 执行确认
- 进度反馈
- 失败解释

### P5-B：复杂任务规划与执行

目标任务不应只限于一句“把红色方块放到右边”。
必须至少支持一类多步复杂任务，例如：

- 连续多物体处理
- 带条件判断的抓取流程
- 执行失败后切换恢复或追问

### P5-C：动态调整

系统必须能够基于世界状态和感知反馈动态调整，而不是只执行固定脚本。

## 8. OpenSpec 开发规范

本节从现在开始对后续 OpenSpec change 生效。

### 8.1 每个 change 必须回答的七个问题

1. 当前 change 属于哪个 phase
2. 它服务于最终智能体目标的哪一段能力
3. 它影响哪些资产
4. 它会让哪些资产状态发生变化
5. 它依赖哪些已冻结资产
6. 它明确不做什么
7. 它如何验证

### 8.2 每个 change 最低文档要求

每个 post-cutover change 的 `proposal.md` 和 `design.md` 都必须包含：

- `Upstream References`
- `Asset Impact`
- `Freeze Delta`

且必须引用：

- `docs/architecture/final_agent_system_architecture.md`
- `docs/governance/asset_governance_and_freeze_rules.md`
- `docs/governance/project_asset_registry.yaml`
- `doc/开发任务拆解_v_1.md`

### 8.3 change 选题规则

允许的 change 类型：

- `freeze-*`
- `verify-*`
- `implement-*`
- `integrate-*`
- `govern-*`

推荐原则：

- 一个 change 只跨一个主阶段
- 验证类 change 不要混入大规模实现
- 运行时 change 不要夹带云端能力
- 云端 change 不要绕过板端边界

### 8.4 资产状态变更规则

如果 change 会改变某项资产状态，必须：

1. 先更新资产总表
2. 在 `Freeze Delta` 里写清楚从什么状态变成什么状态
3. 提供证据来源

### 8.5 冲突处理规则

如果某个 change 想做的事情与上位文档冲突：

1. 先更新上位文档或记录冲突
2. 再修改 OpenSpec artifacts
3. 最后再做实现

### 8.6 禁止事项

以下行为视为不合规：

- 资产未入表就直接实现
- `verified_not_frozen` 资产被默认当成稳定底座
- 从 legacy/demo 直接抽代码进正式主线而不显式登记
- 板端还未冻结就开始接云端规划
- 未有结构化世界状态就直接扩大自然语言能力范围
- 未有 adapter 边界就直接让运行时拼接底层控制

## 9. 当前阶段判断与下一步方向

当前项目状态已经进入：

- `Phase 2：正式 board adapter 与配置资产冻结`

当前已允许推进的工作：

- 继续推进正式 board adapter 与 board-backed integration
- 收口 Phase 2 的 contract、transport、config、calibration 和 adapter 验证
- 将 meeting-demo 增量明确保留为 demo-only 资产，不让其静默回流为正式主线
- 在 frozen foundation 之上继续扩展正式 board-side 执行能力

当前明确禁止推进的工作：

- board runtime / BT 主实现
- 云端对话与规划实现
- VLA 接入
- 把 `src/jetarm_demo_agent` 或 `remote/jetarm_executor` 的 demo 编排静默当成正式 runtime / cloud protocol

当前主线判断是：

- 最终目标仍然是自然语言复杂任务智能体
- 但正式主线当前只允许继续 `Phase 2`
- meeting-demo 已完成并保留为演示层参考，不再驱动正式主线方向

## 10. 当前一句话结论

当前主线不是继续堆演示功能，也不是急着做会说话的壳。
当前主线是按照资产治理和阶段 gate，把 JetArm 逐步做成一个**最终能够通过自然语言与人协作、理解意图、自动规划并完成复杂任务的正式智能体系统**。
